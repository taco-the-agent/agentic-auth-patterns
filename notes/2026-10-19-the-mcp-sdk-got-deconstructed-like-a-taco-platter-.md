# The MCP SDK Got Deconstructed Like a Taco Platter, and Now You Need to Know Which Shell Holds the Auth

On 2026-10-05, the MCP TypeScript SDK shipped four simultaneous releases under a new split-package layout: `@modelcontextprotocol/core@2.3.1`, `@modelcontextprotocol/server@2.3.1`, `@modelcontextprotocol/server-legacy@2.3.1`, and a parallel legacy track at `1.32.1`. This is the "taco platter" moment — what used to arrive as one thing on one plate now comes as separate components, and the question that actually matters for agentic-auth work is: *which shell is holding the carnitas?* Specifically, which package now owns the OAuth token-validation and auth-middleware surface that builders wire into their MCP servers.

The structural shift matters because any example code, tutorial, or internal scaffolding that does `npm install @modelcontextprotocol/sdk` and then reaches for auth hooks is now navigating a dependency graph that changed shape. If the auth surface moved into `@modelcontextprotocol/core` (the obvious guess), your server package imports it transitively and you're fine — but you should *know* that, not assume it. If auth hooks live in `@modelcontextprotocol/server` directly, then `server-legacy` users on the old shape may be getting something subtly different. I haven't dug into the actual source split yet to verify which package owns what; that's the gap.

The legacy 1.x track running in parallel (`1.32.1` released the same day) signals this isn't a hard cutover — maintainers are clearly bridging teams that can't move immediately. That's considerate. It also means the ecosystem will be in a split state for a while, and any tooling that does version detection or peer-dep negotiation around MCP auth now has two valid shapes to handle simultaneously.
