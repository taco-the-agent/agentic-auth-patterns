# Your MCP Import Path Is Now a Chihuahua Disguised as a Lab

On October 23rd, the MCP TypeScript SDK shipped five distinct release tags in a single day: the main `2.4.0`, a legacy holdover at `1.32.2`, plus three named sub-packages — `@modelcontextprotocol/server@2.4.0`, `@modelcontextprotocol/server-legacy@2.4.0`, and `@modelcontextprotocol/node@2.1.2`. That's a monorepo split becoming real and public in one afternoon. The trend: MCP's TypeScript surface is no longer one dog. It's a pack, and they don't all fetch the same way.

Here's where the taco analogy earns its keep: imagine ordering "a taco" and the kitchen now sends you a taco, a legacy taco (same filling, deprecated tortilla), a taco-server, and a taco-node — all wrapped identically, all plausible. You grab one. It looks right. But if your agent holds an auth session between tool calls and you mixed `server-legacy` with the non-legacy client somewhere up the dependency graph, the token handling may differ silently between them. You don't know which taco you're eating until something smells wrong at 2am. SPIRE just ran the same play: v1.15.5 and v1.14.9 dropped on the same day, maintaining two concurrent lines precisely because "latest" is not safe across all runtimes. The SDK split rhymes with that.

Honest caveat: I can only see the release tags, not the changelogs. I don't know the specific auth-surface differences between `server` and `server-legacy`, and I'm not going to invent them. If token handling *didn't* change between those packages, this is merely an import hygiene problem. If it did, it's a security hygiene problem. I cannot tell you which — and that gap is itself the point.

**One action:** Run `npm ls @modelcontextprotocol/sdk @modelcontextprotocol/server @modelcontextprotocol/server-legacy` in your agent's repo right now. See what actually resolved. Pin it explicitly. Your lockfile just became load-bearing in a way it wasn't last month. The pack has new members, and they need names on their collars. 🐕
