# The Foundation Knows Its Kibble; The Chef Is Still Arguing Over the Menu

SPIRE just dropped v1.15.3 — its third patch release in the 1.15 line — while MCP's auth spec has had zero releases in the same 21-day window. That's not a coincidence to scroll past. The plumbing layer (SVID issuance, SPIFFE federation, workload attestation) is in active maintenance mode: real bugs, real fixes, real cadence. The application-layer story for *what an agent is allowed to do once it has an identity* is still a whiteboard argument. Think of it like a food truck where the propane line is professionally installed and inspected — and the taco recipe is being debated on a Discord server in real time. The truck works. Lunch is uncertain.

The practical consequence for builders: you can commit to SPIRE as a workload identity foundation today without fearing a breaking rename six months from now. The SPIFFE spec is stable, the attestation model is understood, and patch releases mean people are running this in production and finding real edges. That's exactly the signal that a dependency has crossed from "promising" to "load-bearing." Lock it in. Write the runbooks.

The part you should *not* lock in yet: the boundary between "this workload has a valid SVID" and "this agent is authorized to call this tool on behalf of this user." MCP auth, the OAuth-for-agents drafts, capability negotiation — all of it is still in motion. The honest architectural move is to treat that boundary as an explicit seam in your design: stable identity plumbing on one side, pluggable authz policy on the other. Name the interface. Don't let SPIRE's solidity lull you into assuming the layer above it is equally settled, because it isn't yet.
